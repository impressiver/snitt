RULING R1 (append-only vs update): JSONL cannot update in place, so recording an outcome on stop means appending a SECOND record with the same sessionID. Task 5's implementer chooses the shape and documents it; the constraint is that AuditLog.recent must still read sensibly and a reader must be able to tell an in-flight session from a completed one. I am NOT prescribing it because the alternative (last-write-wins collapse at read time vs two records surfaced separately) is a genuine trade a reviewer should weigh. Cost if wrong: one refactor of a JSONL reader with its own tests.
RULING R2 (subsystem prefix is a wire contract): Task 4 filters log entries by SnittLog.subsystem prefix, so a module that invents its own root vanishes from every exported bundle WHILE LOOKING CORRECT IN THE CONSOLE. That is a silent-wrongness shape. Task 3's subsystemsSharePrefix test is the guard; it must stay, and any new target must be added to it. Cost if wrong: an entire module's logs missing from support bundles with no error anywhere.
RULING R3 (audit log path): neither task owns where the audit log lives. Task 5 writes it, Task 4 reads it, and both take it as a parameter in the plan -- which is right for testability but leaves production with no single answer. Task 5's implementer decides the production location (Application Support, beside the app's other state) and BOTH call sites must reference one constant, not two string literals. This is the same shape as M4a's AudioTrackOrder: when two sides must agree on a value, name it once. Cost if wrong: diagnostics reads an empty file while sessions are audited to a different path -- and the bundle would report "no agent sessions" for a machine that has run hundreds.

SPIKE S8 answered M5a's load-bearing question BEFORE the plan: OSLogStore(scope:.currentProcessIdentifier) reads our own entries with no entitlement, exposing subsystem/category/level/message. But that scope sees ONLY THE CALLING PROCESS, so `snitt diagnostics export` running in the CLI would bundle the CLI's own log lines and none of the app's -- a feature that looks like it works and contains nothing useful. Diagnostics therefore runs IN THE APP over the socket, the same thin-client rule S5 established for capture, arriving for a different reason: there TCC, here process scope.
S8 also found OSLogStore(scope:.system) succeeds from a developer-launched test binary. DELIBERATELY UNUSED and recorded as such -- a notarized, sandboxed or hardened-runtime app is a different security context, and the next person must not "discover" it and take a dependency on it.
SCOPE: M5a is diagnostics only. Notarization and Sparkle are M5b -- they need an Apple Developer account, a signing identity, and a hosting decision, which are the user's to provide. Opt-in crash reporting is also deferred: it needs a reporter, a server, and a privacy decision about what leaves the machine, and a settings toggle with nothing behind it would be a lie in the UI.
