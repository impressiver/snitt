CRITICAL, and it is MY bug, from the plan's own code: `guard bytes <= Double(Int.max) else { return nil }; return Int(bytes)` traps on parse("9223372036854775807"). Double(Int.max) is not exactly representable and rounds UP to 2^63, so the guard admits a value one greater than Int.max and the conversion then traps. Reviewer verified live in a scratch worktree. This is the literal value of Int.max, not a contrived edge.
Fix: `guard let result = Int(exactly: bytes.rounded(.down)) else { return nil }` -- ask Swift whether the conversion is exact instead of comparing against a rounded bound. rounded(.down) preserves parse("1.1b") == 1.
IMPORTANT: the three nan/inf/1e400 assertions in nonFiniteRefused are DECORATIVE against the specified mutation. Reviewer traced it: those strings are rejected by the character-class filter (n, a, i, f, e are neither digits nor dots) BEFORE Double(number) is ever reached, so they never exercise the overflow bound. A mutant removing only `bytes <= Double(Int.max)` while keeping isFinite passes all six tests. The guard containing the bug had ZERO coverage -- which is exactly why a correctly-run mutation check did not find it.
LESSON, instance #13 and a new variant: a test can be decorative not because it asserts the wrong property but because an EARLIER guard short-circuits it. The assertion looks like it covers the overflow bound; the input never gets there. Checking that a test discriminates is not enough -- you must also check it reaches the code it claims to guard.
Credit where due: haiku transcribed the plan faithfully and reported the partial mutation result honestly (4 assertions failed in one test, 1 in the other). That asymmetry is what surfaced this. A report that rounded up to "mutation check passed" would have shipped the trap.
